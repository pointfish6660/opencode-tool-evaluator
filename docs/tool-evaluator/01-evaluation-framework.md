# 6 维度评估框架

## 概述

Tool Evaluator 的评分框架基于对 **20+ 个评估体系**的系统调研与聚类归纳。我们的目标不是发明一个新的评分体系，而是从现有最佳实践中提炼出一套面向 **AI 开发工具安装前评估**的实用框架。

### 框架开发过程

1. **广度调研**：覆盖 4 大类评估体系 — MCP 服务器评估（5 个）、Claude Skill 评估（9 个）、OpenSSF Scorecards（18 项）、社区共识（HN/Reddit）
2. **信号聚类**：将所有检查项按语义归类，合并重叠信号（如 "贡献者数"在 AgentRank、Skill Grader、NimbleBrain 中均出现）
3. **正交提炼**：筛选出互相独立、覆盖完整决策链的 6 个维度
4. **权重校准**：参考 AgentRank 的权重分配（新鲜度 25% + Issue 健康 25% + 反向依赖 25% + Stars 15% + 贡献者 10%），结合 AI 工具的特殊性（兼容性门控、安全高风险）调整

### 设计目标

- **决策导向**：每个维度都直接影响"装不装"的决策，不包含纯学术指标
- **可量化**：每个维度都有可观测的信号源（GitHub API、仓库文件、社区帖子）
- **平台针对**：兼容性维度专门针对 OpenCode / Claude Code / Cursor 生态
- **快速收敛**：6 个维度可在 5 分钟内完成评估，不需要长时间调研

## 维度 1：OpenCode 兼容性（权重 15%）

### 定义

评估工具是否能正常运行在目标平台上（OpenCode / Claude Code / Cursor），包括协议兼容、依赖可用、平台适配三个方面。这是安装前的**硬性门控**——不能运行的工具不需要评估其他维度。

### 检查项

| 类别 | 检查内容 | 信号来源 |
|------|---------|---------|
| Task 工具依赖 | 是否依赖 Claude Code 专有的 `Task` 工具，有无 fallback | 源码 import / README |
| Hooks 类型 | 使用的是 OpenCode 支持的 hook（`session.idle` / `session.compacting` / `messages.transform`）还是 Claude Code 专有 hook | `package.json` / 源码 |
| MCP 协议 | 是否使用标准 MCP 协议，有无私有扩展 | `mcp.json` / 协议声明 |
| 平台要求 | 是否要求特定操作系统（macOS / Linux / Windows），是否需要原生二进制 | README / release artifacts |
| Shell 假设 | 假设 `bash` / `zsh` / `pwsh`，是否与目标环境一致 | 脚本 shebang / 文档 |
| OpenCode 配置 | 是否提供 `opencode.json` / `opencode.jsonc` 示例 | 仓库文件 |

### 评分示例

| 得分 | 场景描述 |
|------|---------|
| 90-100 | 标准 MCP 协议、无专有依赖、平台无关（纯 Bash/Node/Python）、明确支持 OpenCode |
| 70-89 | 标准 MCP + 小范围平台限制（如仅 macOS）但提供源码构建路径 |
| 50-69 | 使用 Claude Code hook 但有 OpenCode 适配方案、需要手动调整配置 |
| 30-49 | 强依赖 `Task` 工具、仅支持 Claude Code、README 声明多平台但实际只有单平台 hook |
| 0-29 | 需要平台专有二进制（`.exe` / `.app`）且无源码构建、使用宿主内部 API |

### 一票否决规则

> ⚠️ **兼容性维度得分 < 50 时，强制 verdict = 🔴 Skip**，无论加权总分多高。

**理由**：兼容性是二元问题——能运行或不能运行，没有中间状态。一个功能满分但无法安装的工具，对用户的价值为零。将兼容性设为一票否决而非简单的高权重，避免了"其他维度极高分补偿兼容性低分"的误判。

### 边界情况

| 情况 | 处理方式 |
|------|---------|
| 工具是通用 CLI，与 OpenCode 无关 | 仍按通用平台兼容性评估（Linux/macOS/Windows） |
| 工具声明支持 OpenCode 但无示例 | 得分不超过 70（声明无证据） |
| 工具需要特定版本的上游平台 | 记录版本约束，评分依据当前版本兼容性 |
| 工具是纯 MCP Server | 重点检查 MCP 协议合规性，减少 hook 检查权重 |

## 维度 2：安全 / 侵入性（权重 25%）

### 定义

评估工具对用户系统的潜在风险，包括系统配置修改、文件系统写入、网络外发、权限范围、依赖信任五个风险类别。**安全是最高权重维度之一**——一个不安全的工具可能比没有工具更糟糕。

### 五类侵入性风险

| 风险类别 | 具体表现 | 检查方法 |
|---------|---------|---------|
| **系统配置修改** | 修改 `~/.config/`、`~/Library/`、`~/.bashrc`、`~/.zshrc`、`settings.json` | `security-scan.sh` 扫描写入路径 |
| **后台进程安装** | 安装 LaunchAgent / LaunchDaemon / systemd unit / cron entry | 搜索 `.plist` / `.service` / `crontab` 模式 |
| **文件系统越界** | 在项目目录外写入文件（用户 home、`/tmp`、`/var`） | 静态分析写入路径 |
| **网络外发** | 向非 GitHub 的外部服务器发起请求（数据外泄风险） | 搜索 `fetch` / `curl` / `requests` 目标 URL |
| **依赖信任** | 捆绑来源不明的预编译二进制、未签名的 release artifacts | 检查 release 页面、依赖锁定文件 |

### 评分信号

**📍 加分信号**（得分 70-100）：
- 文件系统只读访问，写入仅限 `.omo/` 或显式缓存目录
- 任何系统级修改都需用户显式同意（opt-in）
- 沙箱化执行（容器 / `nix` / `bwrap` / `seatbelt`）
- 可重现构建 + 签名 release + 固定依赖版本

**📎 扣分信号**（得分 0-69）：
- 未经同意安装系统级 hook（launchd / systemd / cron）
- 静默修改用户配置文件
- 向非 GitHub 外部服务器发起未声明的网络请求
- 捆绑来源不明的预编译二进制

### 安全扫描检查清单

`security-scan.sh` 脚本执行的检查项：

| # | 检查项 | 严重程度 | 发现时处理 |
|---|--------|---------|-----------|
| 1 | `.plist` / `.service` / `crontab` 文件存在 | 高 | 记录 + 扣 20 分 |
| 2 | `settings.json` 写入操作 | 高 | 记录 + 扣 15 分 |
| 3 | `~/.config/` / `~/Library/` 路径写入 | 中 | 记录 + 扣 10 分 |
| 4 | `fetch` / `curl` / `requests` 指向非 GitHub 域名 | 中 | 记录 + 扣 10 分 |
| 5 | `sudo` / `chmod 777` / `chown` 操作 | 高 | 记录 + 扣 25 分 |
| 6 | 未签名的二进制文件 | 高 | 记录 + 扣 20 分 |
| 7 | `eval` / `exec` 执行远程代码 | 极高 | 记录 + 强制 ≤30 分 |

### 为什么权重 25%（最高）

安全维度与维护健康维度并列为最高权重，理由：
1. **不可逆性**：安全事件（数据泄露、系统破坏）的后果不可逆，而功能不足只是"不好用"
2. **外部性**：不安全工具的风险由用户承担，而非工具开发者承担
3. **信息不对称**：用户难以自行验证工具的安全性，需要评估器作为可信中介
4. **行业共识**：OpenSSF Scorecards（18 项检查中 9 项关于安全实践）和 skillchecker（35 条 CRITICAL 规则）都把安全放在首位

## 维度 3：维护健康（权重 25%）

### 定义

评估工具是否被积极维护，包括代码更新频率、Issue 响应速度、贡献者多样性、生态依赖度四个信号。参考 **AgentRank** 的五信号权重体系。

### AgentRank 信号体系

| 信号 | AgentRank 权重 | 我们的检查方式 |
|------|---------------|--------------|
| 新鲜度 | 25% | 最后提交时间（GitHub API） |
| Issue 健康 | 25% | 最近 100 个 Issue 的关闭率 + 平均响应时间 |
| 反向依赖 | 25% | GitHub "Used by" 计数 |
| Stars | 15% | Star 数量 + 增长趋势 |
| 贡献者 | 10% | 贡献者数量 + 最近活跃贡献者 |

### 评分示例

| 得分 | 场景描述 |
|------|---------|
| 90-100 | 最后提交 <1 月、Issue 关闭率 >80%、10+ 贡献者、100+ 反向依赖、季度 release |
| 70-89 | 最后提交 <3 月、Issue 关闭率 60-80%、3-10 贡献者、维护 CHANGELOG |
| 50-69 | 最后提交 3-6 月、Issue 关闭率 40-60%、单一贡献者但有 bus-factor 缓解 |
| 30-49 | 最后提交 6-12 月（停滞）、Issue 关闭率 <50%、Issue 90 天无回复 |
| 0-29 | 最后提交 >12 月（归档）、无 CHANGELOG、无 release、单贡献者无缓解 |

### 维护信号的解读原则

| 信号 | 正面解读 | 负面解读 |
|------|---------|---------|
| Stars 多 | 广泛使用，社区活跃 | 可能是炒作或早期热度，需配合 issue 健康度 |
| 贡献者多 | Bus factor 风险低 | 可能是 drive-by 贡献，需看核心维护者数 |
| Issue 多 | 社区关注度高 | 可能是 bug 太多，需看关闭率 |
| Release 频繁 | 积极迭代 | 可能是质量不稳定，需看 changelog 内容 |

### 为什么权重 25%

与安全并列为最高权重：
1. **Bus factor 风险**：单一贡献者的项目随时可能停止维护
2. **兼容性漂移**：上游平台（OpenCode / Claude Code）频繁更新，不维护的工具很快失效
3. **Issue 沉默 = 潜在 bug**：未回应的 Issue 意味着已知 bug 未修复
4. **AgentRank 实证**：该信号体系在 MCP 服务器评估中被多次验证有效

## 维度 4：功能价值（权重 15%）

### 定义

评估工具解决的问题是否真实、方案是否有效、相对现有方案是否有增量价值。这是主观性最高的维度，通过**差距分析**（Gap Analysis）和**价值评估**（Value Assessment）两个步骤降低偏差。

### 差距分析法

1. **问题声明**：工具声称解决什么问题？
2. **现有方案**：解决同一问题的已有工具（包括通用工具）
3. **增量价值**：相对现有方案的差异化在哪里？是更便宜、更快、更准确，还是覆盖新场景？
4. **证据验证**：README 营销声明 vs 实测数据（benchmark / Issue 反馈 / 社区评价）

### 评分信号

**📍 加分信号**（得分 70-100）：
- 解决真实且明确表述的问题，无直接等价替代
- 提供可重现的 benchmark 数据支持 README 声明
- 多场景演示（非单点工具）
- 社区中有真实用户的正面反馈（非仅 star 数）

**📎 扣分信号**（得分 0-69）：
- README 使用"agentic"、"autonomous"等营销词但无证据
- 实测数据（Issue / benchmark）与营销声明矛盾
- 单一用途工具，解决已有工具覆盖的小众问题
- 工具数量通过简单包装同一原语膨胀（凑数）

### 为什么权重 15%

功能价值重要但主观性强，过高的权重会放大评估者偏差。15% 让功能价值在总分中有影响但不主导，配合一票否决和加权计算实现平衡。

## 维度 5：文档与 UX（权重 10%）

### 定义

评估工具的文档质量和上手体验，包括 README 完整度、示例可运行性、CHANGELOG 维护、安装指南质量。

### 可读性检查清单

README 应包含以下六个标准段落：

| 段落 | 检查要点 |
|------|---------|
| 问题说明 | 一句话说清解决什么问题 |
| 安装步骤 | 复制粘贴可执行，列出所有前置依赖 |
| 使用示例 | 覆盖至少 2 个典型场景，命令可直接运行 |
| 配置说明 | 所有可配置项及其默认值 |
| 常见问题 | 已知限制和故障排查 |
| 许可证 | 明确的开源许可证 |

### 评分信号

**📍 加分信号**（得分 70-100）：
- README 覆盖全部六段，附截图或动画演示
- 示例在全新 clone 后可直接复制粘贴运行
- 双语文档（至少英文 + 一门其他语言）或有明确翻译政策
- 有故障排查章节覆盖已知问题

**📎 扣分信号**（得分 0-69）：
- README 缺少安装步骤或使用示例
- 示例引用已失效的分支、token 或路径
- 仅中文或仅英文，无翻译路径
- 无安装指南，用户需从 Issue 中逆向工程

## 维度 6：运营成本（权重 10%）

### 定义

评估工具引入后的持续运营成本，包括 Token 消耗、订阅费用、资源占用三类。来源于 **社区共识**（HN / Reddit 上对 MCP 服务器 token 污染和付费 API 依赖的真实痛点）。

### 成本类别

| 类别 | 具体表现 | 影响范围 |
|------|---------|---------|
| **Token 消耗** | MCP Server 即使不使用也会污染上下文（community 共识：控制在 3-6 个服务器）；每次调用消耗 50K+ token 会快速烧完额度 | 每次会话 |
| **订阅费用** | 依赖付费 API（OpenAI / Anthropic / GitHub Enterprise）无免费层 | 每月 |
| **资源占用** | 重 CPU / GPU / 磁盘负载，影响笔记本电脑正常使用 | 持续 |
| **冷启动** | MCP Server / CLI 工具的初始化延迟 | 每次调用 |
| **网络依赖** | 需要持续网络连接，离线不可用 | 每次调用 |

### 评分信号

**📍 加分信号**（得分 70-100）：
- 免费开源，无付费上游服务
- 安装后本地运行，无网络依赖
- 低资源占用（秒级完成、<100 MB 内存）

**📎 扣分信号**（得分 0-69）：
- 需要付费 API 订阅（无免费层）
- 每次请求消耗 >50K token（大上下文加载）
- 重 CPU / GPU / 磁盘使用，影响笔记本工作流

## 评分公式

### 加权总分计算

```
weighted_total = 0.15 × D₁ + 0.25 × D₂ + 0.25 × D₃ + 0.15 × D₄ + 0.10 × D₅ + 0.10 × D₆
```

其中 D₁ 至 D₆ 分别为六个维度的 0-100 分值，结果四舍五入为整数。

### 权重总和验证

| 维度 | 权重 |
|------|------|
| 兼容性 | 15% |
| 安全 | 25% |
| 维护 | 25% |
| 功能 | 15% |
| 文档 | 10% |
| 成本 | 10% |
| **合计** | **100%** |

## Verdict 判定规则

按顺序匹配，第一个命中的规则生效：

| Verdict | 条件 | 含义 |
|---------|------|------|
| 🟢 **Install** | 加权总分 ≥ 80 **且** 兼容性 (D₁) ≥ 50 | 推荐安装 |
| 🟡 **Hold** | 加权总分 60-79；或总分 ≥ 80 但兼容性 <50 且已有 fork/wrapper 方案 | 观望，等待改进或替代 |
| 🔴 **Skip** | 加权总分 < 60；**或** 兼容性 <50（一票否决） | 不推荐安装 |

### 一票否决规则说明

兼容性维度（D₁）得分低于 50 时，**强制 verdict = 🔴 Skip**，无论加权总分多高。这是框架中唯一的硬性否决机制。

**设计依据**：
- 兼容性是二元门控：能运行或不能运行
- 避免其他维度极高分"补偿"兼容性低分导致误判
- 与 Skills_Curator 的 `--check` 前置检查和 skills-compat-manager 的跨平台兼容层理念一致

## 权重选择依据

### 为什么安全 + 维护 = 50%

安全（25%）和维护（25%）合计占总权重的 50%，这是有意设计：

**可信度优先原则**：一个不安全或无人维护的工具，功能再强也不能引入。这两项是**可信度的核心代理指标**（proxy for trustworthiness），在决策权重上必须超过半数。

**实证支持**：
- AgentRank 将新鲜度 + Issue 健康（维护信号）赋权 50%
- OpenSSF Scorecards 18 项检查中 9 项关于安全实践（50%）
- skillchecker 35 条规则全部是安全相关（100%）

### 为什么兼容性只有 15%

兼容性虽然重要（通过一票否决机制保障），但在**通过门控后**的评分阶段不需要继续占主导。15% 的权重让兼容性在加权总分中有影响但不主导，避免重复惩罚（一票否决已经处理了严重不兼容的情况）。

### 为什么功能价值只有 15%

功能价值的主观性最高，且容易受评估者个人偏好影响。15% 让功能价值在总分中有影响但不过度，配合差距分析法（Gap Analysis）尽可能客观化。

### 为什么文档 + 成本只有 20%

文档和成本属于**辅助维度**——影响长期体验但不决定生死。过高的权重会让一个"文档好但安全差"的工具得分偏高，违反可信度优先原则。
